# `zcode serve`: daemon and embedded instances (opt-in)

One resident process hosting many agent instances on the same in-memory bus. Instances in the same `group` are agents of one swarm (channels, not the socket); instances in different groups, or without a group, are fully isolated. Nothing starts a daemon automatically.

```
zcode serve          # foreground; Ctrl-C / SIGTERM stops every instance and container, removes the socket and keeps the restart manifests
```

Config (`serve` key of the daemon's own config): `max_instances` (64), `max_history_bytes` (8 MiB per instance; over that the context is compacted before a turn), `event_ring` (2000 events kept per instance), `concurrency` (8 model requests at once, daemon-wide), `max_steps` / `max_tokens` (daemon-wide budgets, unlimited by default), `apps` (`{"name": {"token": "..."}}`; when present every connection must `hello` with a valid app and token).

## What comes from where

* **Everything an instance needs comes from the client's `create` request**: `cwd`, a `config` object (the same schema as a config file: `provider.<id>.options.{baseURL,apiKey}`, `model`, optional `small_model`, `profiles`, `swarm`), `sandbox`, `policy`, `limits`. The daemon's own environment, config files and credentials are never used for an instance (`ZCODE_*`/`OPENCODE_*` model overrides are ignored; `bash` runs with a scrubbed environment even at tier 0).
* The API key lives only inside the daemon. It is never sent to clients (events do not contain it), and never enters a container.
* Model clients (HTTP connection pools) are shared across instances that use the same base URL, key and model; one semaphore bounds model requests daemon-wide and one budget bounds total steps/tokens.

## Socket and framing

`$XDG_RUNTIME_DIR/zcode/zcode.sock` (fallback `/tmp/zcode-<uid>/zcode.sock`), directory 0700, socket 0600, `SO_PEERCRED` checked (same uid only). Frames are the same as the guest protocol: 4-byte big-endian length + a JSON object, at most 8 MiB. Requests carry `req` (a client-chosen id) and `op`; every request gets exactly one reply `{"req":N,"ok":true,...}` or `{"req":N,"ok":false,"err":"..."}`. Events are separate frames without `req`.

## Operations

| op | fields | notes |
|---|---|---|
| `hello` | `app`, `token` | only needed when `serve.apps` is set; instances and groups are namespaced per app |
| `create` | `instance`, `cwd`, `config`, `model?`, `sandbox?` (default `landlock`), `profile?`, `policy?` `{read,write,net,outside}`, `limits?` `{max_time,max_steps,max_tokens}`, `thinking?` (bool, default false: stream the model's reasoning as `reasoning_delta` events; needs `stream`), `sandbox_of?` (name of another instance of this app: share its sandbox/container instead of opening one; closing this instance leaves it open), `container?` `{image, mem, cpus, pids, ports, custom}` (tier 2 only; `custom` is the `container` customization object: `mounts`, `env`, `tmpfs`, ...; layered over the daemon's own `container` config), `group?`, `max_workers?`, `stream?`, `session?`, `close_on_disconnect?`, `reattach?` (if the instance already exists, e.g. restored after a daemon restart, return it `{session, events, reattached}` instead of failing) | allocation only: no model client, sandbox, session file or agent exists until the first `prompt`/`send`/`spawn`. Instance and group names are `[A-Za-z0-9_-]{1,32}` |
| `exec` | `instance`, `command`, `timeout?` (s, default 120, max 3600), `background?` | run one shell command in the instance's sandbox (tier 2: inside its container) and reply `{code, timed_out, output}`. Builds the instance if needed. It shares the agent's persistent shell: wrap state-changing commands in a subshell |
| `build` | `instance` | build the instance now (model client, sandbox, agent, joining its group, so that it can receive messages) instead of at the first `prompt`/`send`/`spawn`. Replies `{agents: [...]}`, the group's agents as `/agents` lists them |
| `attach` | `instance`, `since?`, `catch_up?` | subscribes this connection to the instance's events; the ring is replayed first (events with `seq > since`). With `catch_up: true`, if a turn is in flight the reply says `partial: true` and the replay is followed by one `partial` event `{text, reasoning, step, tools: [{callID, tool, summary, input, done, output?, ok?}], seq, timestamp, instance, agent}` before any live event: the current step's assistant text and reasoning so far (from the deltas, or the whole `text`/`reasoning` event for an instance that does not stream) and its tool calls (`done` + `output`/`ok` once a tool finished; tool results are only reported when the step's calls are all done, so during execution they are `done: false`). The snapshot **replaces** the current step's own events in the replay (`text_delta`, `reasoning_delta`, `text`, `reasoning`, `tool_start`, `tool_use` of the lead after its latest `step_start`), so nothing shows twice; `seq` of the `partial` is the instance's counter at that instant. Idle instance: no `partial`, `partial: false`. Meant to be used with `since` = `status.events` |
| `detach` | `instance` | |
| `prompt` | `instance`, `text` | one turn at a time (`instance is busy` otherwise); the end of the turn arrives as a `turn_end` event |
| `send` | `instance`, `to`, `text` | message an agent of the instance's swarm (a worker or, in a group, another instance); an idle instance wakes up and answers |
| `spawn` | `instance`, `name`, `prompt`, `write?`, `profile?` | same semantics as the tool |
| `thinking` | `instance`, `on?` | show/hide the model's reasoning for the instance from its next turn; without `on` it only reports `{thinking}`. `status` includes `thinking` too |
| `cancel` | `instance` | first drops the messages still queued for this agent (`send`s and worker/peer messages it has not read yet; their count is `status.queued`), then interrupts the running turn. Replies `{dropped, interrupted}`: `dropped` = number of queued messages forgotten (they never reach the conversation and do not wake the instance), `interrupted` = whether a turn was running. A running turn ends by itself with `error` `{type: "interrupted"}` and `turn_end` `{stop: "interrupted", code: 130}` (that is the one `turn_end`; none is added). On an idle instance it is a no-op reply `{dropped: 0, interrupted: false}`, never an error. Messages already read into the conversation, and the instance's workers, are not touched; messages sent after the `cancel` are delivered normally |
| `close` | `instance` | stops workers, closes sandboxes/containers, forgets the instance |
| `status` | `instance?` | state, queue, per-agent budgets (as `/agents`); per instance also `pid` (host pid of the tier 2 container init, for `nsenter`) and `ports` (`[{guest, host}]`), `turn` (`null` when idle, else `{since, step, tool}`: `since` = ms when the turn began, `step` = `step_start`s seen this turn (0 before the first), `tool` = name of the tool executing now, the latest started one when several run in parallel, else `null`), `queued` (messages for this agent not yet read; always 0 without a swarm) and `last_event_ts` (`timestamp` of its newest event, `null` if it has none). `running`, `events`, `thinking`, ... are unchanged |
| `history` | `instance`, `before?`, `limit?` (default 200, max 1000), `agent?` | the conversation as UI items, read from the instance's session file, so a client needs no filesystem access, and it works before the instance is built and after a daemon restart. Replies `{items, first, total}`: `items` are the `limit` items ending before index `before` (default: the end), `first` is the index of `items[0]`, `total` the number of items; page backwards with `before = first`. Items: `{"k":"user","text"}` (also `[from x]` / `[system]` messages the agent was given), `{"k":"text","text"}` (assistant text), `{"k":"tool","id","tool","input","output","ok"}`: a tool call paired with its result by call id (in order when an id does not match; `output` and `ok` are `null` while it has no result; `ok` is false when the output starts with `Error:`). Any text, output or input string over 12000 chars is cut and the item gets `"cut": true`. System prompts and reasoning are not items. The history is what the session file holds: after a compaction it starts with the summary. `agent` = a worker's name returns its own conversation. An instance without a session file yet has `{items: [], first: 0, total: 0}` |

## Interactive agents in a group (`zcode --group`)

`zcode --group NAME [--agent AGENT] --auto` is a client of this protocol for people: it `create`s an instance named after the agent with `group`, `stream: true` and `close_on_disconnect: true`, calls `build` so the agent is in the group and answers messages at once, `attach`es, and then forwards each line you type as a `prompt` and renders the event stream. It needs a running daemon (`zcode serve`) and `--auto`, because the daemon cannot ask for permission.

`zcode --attach INSTANCE` (starts from the current end of the event ring, shows reasoning when the instance has `thinking` on, `/thinking on|off` toggles it) is the same interface for an instance another client already created (with its own model, sandbox and limits): it loads no config, only `status`/`build`/`attach`es and forwards lines as `prompt`s, and leaving sends `detach`, never `close`. Instances created without `stream` show each step's text at once instead of streaming.

Agents of one group share one bus: `send(to, text)` reaches any agent of the group by its instance name, and a message to an idle agent wakes it (the daemon starts a turn: `[from name] ...`), whether or not anyone is typing at it. Group specifics:

* The group has no swarm-wide step, token or time budget (each turn keeps its own `limits`): groups are long-lived.
* The caps on agent-to-agent chatter (`pair_cap`, `total_cap`, `chain_cap`) are re-armed whenever a person's `prompt` arrives, so they stop agents answering each other forever without ending a long conversation between people.
* `close_on_disconnect` ends the instance when the creating connection closes (a terminal that died must not leave an agent answering colleagues with nobody to read it). Without the flag, instances outlive their connection as usual.
* An agent only shares files with a peer whose `cwd` is the same folder; messages carry summaries and paths.

## Events

The `--format json` events (`step_start`, `text`, `tool_use`, `step_finish`, `error`, `reasoning`) plus the swarm events (`spawn`, `message`, `idle`, `port`) and `incoming` (`from`, `text`: a message from another agent was delivered to this instance's agent, before the turn it triggers), each with `instance`, `agent` (the instance name for its lead), a per-instance `seq` and a `timestamp` (ms since the epoch; every frame has one, including `text_delta`, `reasoning_delta`, `tool_start`, `incoming`, `turn_end` and the daemon's own `warning`, `restored`, `closed`). Extra events: `turn_end` `{stop: done|limit|interrupted|error, code: 0|3|130|1, message, text}` (the exit codes of `zcode run`), `warning`, `closed`, `tool_start`; with `stream: true` also `text_delta` and `reasoning_delta`.

* `tool_start` `{tool, callID, summary, input}` is emitted for every tool call of a step before it runs (whether or not the instance streams). `callID` is the id of the later `tool_use` event (`part.callID`) and of the model's tool call, so a client pairs them exactly even when several calls of one step run in parallel; `input` is the parsed arguments object (`null` if they were not valid JSON), with any string over 8000 bytes cut to head + tail like tool output.
* `user` `{text, source, agent}`: what the instance's agent was just asked. `source` is `client` (a `prompt` that was accepted) or `restart` (the `[system]` notice a turn gets after a daemon restart; a restored worker gets the same, with `agent` = the worker). It goes into the ring **before** the turn's first `step_start`, so replays and late attachers see it. A `prompt` refused (`instance is busy`) emits nothing. Turns woken by agent messages (`send`, workers' reports) emit no `user` event: they produce `incoming` events. Clients must ignore event types they do not know; the thin clients (`zcode run`, `--group`, `--attach`) do, and `zcode run --format json` filters daemon-only types so its output stays identical to the embedded stream.

## Lifetime and limits

* **Restarts.** The daemon writes one manifest per instance to `$XDG_STATE_HOME/zcode/daemon/<app>__<name>.json` (0600: it holds the `create` request, API key included): the request, its workers (name, prompt, write paths, profile, running/idle), the event counter and whether a turn is in flight. It is rewritten (debounced) on every turn start/end, spawn, idle and every 50 events, and removed by `close`. A graceful stop (SIGINT/SIGTERM) writes them last, tears down agents and containers and keeps the files; a crash or SIGKILL leaves the last ones (containers die with the daemon either way, see `TIER2.md`). On the next `zcode serve`:
  * every instance is registered immediately (clients can `status`/`attach`/`create` with `reattach` at once); the event counter resumes 100 above its saved value, so a client's `since` cursor stays valid (the ring itself is not persisted);
  * agents are rebuilt in the background: instances in a group, with workers, or mid-turn eagerly (new containers, group membership, workers respawned with their own session), the others on first use. A `restored` event `{running, workers}` is emitted;
  * conversations come from the session files (the daemon now resumes an existing `session`; a history ending in tool calls without results is repaired with an `interrupted` result);
  * a turn that was in flight is continued by a `[system]` message saying the daemon restarted and the sandbox was recreated; a worker that was working gets the same, an idle one waits for its next message;
  * lost: processes and background jobs in containers, the shell cwd, container-only files (the overlay layer is dropped), queued undelivered agent messages, the swarm/daemon budget counters.
  * An instance created with `close_on_disconnect` is restored too; the terminal (`zcode --group`) reconnects by itself (it retries for about a minute, `create` with `reattach`, `build`, `attach` since its last `seq`). Nobody owns a restored instance until then: close it with `close` if its terminal never returns.

* Instances outlive connections and are re-attached by id; a dead client never takes its instances down.
* `max_instances` caps the number of instances; history is compacted over `max_history_bytes`; tool output is capped (30 KB per call, the rest spilled to a file); `event_ring` bounds the replay buffer.
* A panic inside one instance's turn is caught at the task boundary: that instance reports an `error` + `turn_end` and refuses further prompts, the daemon and other instances keep running. This needs `panic = "unwind"`: build the daemon with `cargo build --profile serve` (release plus unwinding; +~0.5 MB binary, +~0.3 MB idle RSS). The default release profile keeps `panic = "abort"` to protect the startup/RSS budget, and `zcode serve` prints a note when it was built that way: there a panic stops the whole daemon.

## `zcode run` as a thin client

`zcode run --auto ...` connects to the daemon when its socket answers: it sends its own resolved config (its env and files already applied) in `create`, attaches, prompts, renders the event stream and exits with the turn's code; `--format json` output is the embedded stream (without the daemon-only `instance`/`seq` fields). With no daemon, a stale socket, `ZCODE_NO_DAEMON=1`, `--continue`/`--session`, or without `--auto` (a daemon cannot prompt your terminal), it falls back to the embedded runtime. Human output is rendered from streamed deltas, so it matches the embedded output except for the colored edit diffs.
